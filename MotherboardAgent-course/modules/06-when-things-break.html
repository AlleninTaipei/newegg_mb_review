When Things Break

Every pipeline in this course has worked so far. Real ones don't always. Here's how this codebase tells you what went wrong, and how to read it like a flight recorder.

The black box, not the crash

When a plane has a bad flight, investigators don't rebuild the plane from scratch. They pull the flight recorder and check exactly which system logged an anomaly, and when.

This codebase leaves the same kind of breadcrumbs: print statements, per-region failure messages, and quiet skips instead of guesses. This module teaches you to read them.

Everything worked. Until it doesn't.

Across five modules, every scraper ran, every dashboard built, every email sent. In the real world, websites redesign their pages, network requests time out, and one region's step can fail while the other two succeed fine.

This module is about the signals this codebase already gives you for exactly that moment, so you never have to guess what broke.

Three simple shapes, not one clever framework

This codebase's failure handling is intentionally simple and visible, not clever and hidden. Missing data is silently skipped, one region failing doesn't take down the other two, and a failed step is reported by name.

Recognizing these three shapes helps you tell normal, expected degraded operation apart from an actual bug.

Shape 1: skip, don't guess

When a product's price or rating can't be parsed, the scraper drops that one item rather than saving it with a made-up value like $0.00. It would rather under-report than lie.

CODE 
            price  = parse_price(item)
            rating = parse_rating(item)
            if price is None or rating is None:
                continue
PLAIN ENGLISH

Try to read this item's price, and try to read its rating.

If either one couldn't be read, meaning it came back empty...

...skip this one item entirely and move to the next. Don't save it with a fake or blank number.

This is a deliberate design choice. A missing motherboard in tomorrow's dashboard is a minor gap; a motherboard listed at a fake $0.00 price is a lie that spreads into every downstream chart and email.

Shape 2: one region's failure stays contained

A network hiccup while scraping one brand is caught as an exception instead of crashing the whole program. It's logged with the brand's name attached, then that one brand's loop stops early.

CODE 
        try:
            resp = requests.get(url, headers=HEADERS, timeout=20)
            resp.raise_for_status()
        except requests.RequestException as exc:
            print(f"  [{brand}] Request error: {exc}")
            break
PLAIN ENGLISH

Attempt the request, and check that the response wasn't an error page.

If the request itself failed, catch that failure by name instead of letting the program die.

Print exactly which brand failed and why, then stop just that brand's scrape.

Zoom out one level and the same shape repeats at the shell script level. Each region's chain of scripts reports its own name if it fails, and the final step waits on all three regions individually so one failure never hides the other two's results.

Shape 3: failures are logged by name

run_all.sh never just says "something failed." It says which region and which script, so you know exactly where to look first.

CODE 
run_pipeline() {
    local region=$1; shift
    for script in "$@"; do
        echo "[${region}] ${script} ..."
        if ! python3 "${script}"; then
            echo "[${region}] FAILED at ${script}" >&2
            return 1
        fi
    done
    echo "[${region}] all done"
}
PLAIN ENGLISH

This function runs one region's chain of scripts in order, one at a time.

If any single script in that chain fails, print exactly which region and which script.

Stop that region's chain right there, but don't touch the other regions.

How to debug a failure

When something looks wrong tomorrow morning, work through these four questions in order. Each one points at a specific place to look, not the whole system.

1
Which region failed?

Check run_all.sh's output for a line like [Kakaku] FAILED at generate_kakaku_dashboard.py. That names the exact region and exact script, so you only need AI to look at that one log.

2
Did a product just go missing?

That's usually not a crash. Check whether its price or rating parsed as None and got silently skipped, the same shape you saw above, not a sign the scraper is broken.

3
Did the whole scrape return zero products?

That's a bigger signal. It usually means the website changed its layout, breaking a CSS selector like .item-container or .item-rating i that the scraper depends on to find things on the page.

4
Want to add a 4th region?

Copy the scraper, generator, and sender trio from an existing region, adjust the schema fields for that market's metric (like Danawa's store_count), then add one line to run_all.sh and one recipient variable to the GitHub Actions workflow.

A website redesign is the one failure this codebase can't route around on its own, because it changes the shape of the page the selector was written for. Everything else, missing fields, one bad request, one failed script, is handled by the three shapes above.

💡
Key Insight

This system's resilience doesn't come from one big clever error-handling framework. It comes from small, boring choices made consistently: skip instead of guess, isolate failures per region, and log every failure by name. The simplest failure handling is usually the most debuggable one.

What you now know

Back in Module 1, the hook was a 9am email arriving automatically, with nobody touching a keyboard. Now you know everything standing behind that one email: three regions running as concurrency, each one hitting its own endpoint, structuring results into a schema, running dedup and diff to catch what changed, and finally getting scheduled by cron so it all happens while you're asleep.

And now, when one morning that email doesn't look right, you know exactly where to look: the per-region log, the silent skips, or the selectors, instead of just "the scraper is broken."
