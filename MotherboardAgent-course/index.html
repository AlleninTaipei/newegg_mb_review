Your Market Intelligence Robot

One command. Three countries. Your inbox. Here's what actually happens.

Imagine waking up to a motherboard report

Every morning, three markets' worth of motherboard data — prices, ratings, store counts — lands in your inbox as a beautiful interactive dashboard. You didn't click anything. You didn't open a browser. It just appeared.

That's what MotherboardAgent does. It's a pipeline that runs three independent missions in parallel — one for the US (Newegg), one for Japan (Kakaku.com), and one for Korea (Danawa) — each ending with a detailed HTML report delivered to your inbox.

🇯🇵

Why three separate programs instead of one?

Each region runs independently so a failure in Japan (say, Kakaku blocks the scraper) doesn't stop the US report from being sent. Isolation = resilience. This is a classic architectural pattern called decoupling — systems that don't share state can fail independently.

02

The Web Scrapers

How a Python script reads a shopping website like a robot detective.

A browser, minus the human

When you visit Newegg in your browser, here's what actually happens: your browser sends a HTTP request to Newegg's server, the server sends back an HTML page, and your browser renders it visually.

The scraper does the first part — sending the request and receiving HTML — but skips the visual part entirely. Instead, it reads the HTML text and extracts just the data it needs: product names, prices, ratings.

🧑
A human with a browser

Loads page → sees pretty visuals → reads prices with eyes

🤖
A scraper script

Loads page → receives raw HTML text → extracts prices with code

🎭
The scraper pretends to be a browser

The scraper sets a User-Agent header — a label that tells the server what kind of software is making the request. It uses a real Chrome browser's User-Agent string so Newegg treats it like a regular visitor, not a bot.

Knowing where to look

Before the scraper visits a single page, it needs to know which brands to search for and which URLs to construct. Newegg uses a filter system based on "N-values" — numeric codes that represent brands in their catalog.

CODE 
# Newegg N-values (discovered from filter sidebar JSON)
MOTHERBOARD_N = 100006654
BRANDS = {
    "ASRock":  {"n_val": 50001944, "max_pages": 3},
    "ASUS":    {"n_val": 50001315, "max_pages": 5},
    "MSI":     {"n_val": 50001312, "max_pages": 5},
    "Gigabyte":{"n_val": 50001314, "max_pages": 5},
}
PLAIN ENGLISH

This is a comment — a note to humans, ignored by the computer. It explains where these numbers came from.

100006654 is Newegg's internal code for "show me all motherboards" (AMD + Intel combined).

BRANDS is a dictionary — a lookup table. The brand name is the key; the value is another small table with that brand's details.

ASRock's Newegg brand code is 50001944. Only scrape up to 3 pages for ASRock.

ASUS, MSI, Gigabyte each have their own brand codes and get 5 pages scraped each — they have larger catalogs.

The closing brace ends the BRANDS dictionary.

Parsing HTML: reading the page like a map

Once the scraper downloads the HTML text of a Newegg page, it needs to find the product listings inside it. This is where BeautifulSoup comes in. It turns the raw HTML into a tree you can navigate.

CODE 
soup  = BeautifulSoup(resp.text, "lxml")
items = soup.select(".item-container")
if not items:
    print(f"  [{brand}] No items found – stopping.")
    break
PLAIN ENGLISH

Parse the HTML text of the response into a navigable structure called "soup." Use lxml as the parsing engine — it's fast.

Find all HTML elements with the CSS class "item-container" — this is the CSS class Newegg uses for each product card on a listing page.

If the list is empty, nothing was found on this page.

Print a message saying no items were found for this brand.

Stop the scraping loop — no more pages to process.

🔍
CSS classes as treasure map coordinates

Web developers use CSS classes to style groups of elements. Scrapers exploit this: if every product card has class="item-container", you can locate all products at once with .select(".item-container").

The scraper is polite on purpose

Extracting meaning from a product name

Newegg doesn't have separate database fields for "socket" or "chipset." That information is hidden inside the product name: "ASRock X870E Nova WiFi ATX AM5 Motherboard". The scraper reads the name and infers the specs using pattern matching.

CODE 
def parse_chipset(name: str) -> str:
    u = name.upper()
    for cs in [
        "X870E", "X870", "X670E", "Z890", "B860",
    ]:
        if cs in u:
            return cs
    return "Unknown"
PLAIN ENGLISH

Define a function called parse_chipset that takes a product name as input and returns a string (the chipset name).

Convert the name to uppercase so "x870e" and "X870E" both match — case-insensitive search.

Loop through a list of known chipset names in order, most specific first. (X870E before X870, so "X870E Nova" doesn't accidentally return just "X870".)

If this chipset name appears anywhere in the uppercase product name...

Return it immediately — we found it!

If no chipset name matched, return "Unknown" — better to admit ignorance than guess wrong.

🧩
Order matters: most specific first

The list checks "X870E" before "X870." If you reversed this order, "X870E Nova WiFi" would match "X870" first and return the wrong answer. This "most specific first" trick prevents false positives and is a common pattern in parsing logic.

The Data Warehouse

How nine scraped fields become a structured JSON file — the shared language between scraper and dashboard.

JSON: the sticky note that everyone can read

After the scraper visits hundreds of Newegg pages, it needs to save the data somewhere that the dashboard generator can read later. It uses a format called JSON — a text file with a very specific structure that every programming language can read and write.

Think of JSON like a well-organized filing cabinet where every drawer is clearly labeled, every folder has a consistent layout, and any coworker — regardless of their background — can find exactly what they need.

{ }

Object / Dictionary

A set of labeled values. Like a named box: "brand": "ASRock". Keys are always strings in quotes.

[ ]

Array / List

An ordered collection of items. Like a numbered row of shelves: ["ASRock", "ASUS", "MSI"]

42

Number / String

Raw values. Numbers need no quotes: 4.6. Text needs quotes: "X870E".

Inside motherboard_reviews.json

Here's what one product looks like after the scraper is done with it. This is the exact format stored in the file:

JSON STRUCTURE 
{
  "source": "Newegg",
  "retrieved_date": "2026-04-14",
  "brands": {
    "ASRock": {
      "products": [
        {
          "name": "X870E Nova WiFi",
          "socket": "AM5",
          "chipset": "X870E",
          "form_factor": "ATX",
          "rating": 4.6,
          "review_count": 282,
          "price_usd": 259.99,
          "category": "AMD"
        }
      ]
    }
  }
}
PLAIN ENGLISH

The outer object is the whole file. Everything lives inside it.

"source" tells us this data came from Newegg — useful if you ever mix data from multiple sources.

"retrieved_date" is a timestamp — so the dashboard can show "data as of April 14."

"brands" contains one entry per brand scraped. Each brand is its own labeled box.

Inside each brand is a list called "products" — an array of product objects.

Each product is its own object with these labeled fields.

"name" is the product model (brand prefix stripped off).

"socket" — which CPU generation this board supports. Extracted from the product name.

"chipset" — the feature tier of the board. Also extracted from the name.

"form_factor" — the physical size of the board.

"rating" — average star rating (1.0–5.0).

"review_count" — how many reviews have been written. More reviews = more reliable rating.

"price_usd" — price in US dollars, rounded to two decimal places.

"category" — derived from the socket: AM5/AM4 = AMD, LGA = Intel.

Three markets, three different metrics

Not every market measures popularity the same way. The three regional schemas differ in one key column because each site exposes different data:

🇺🇸
Newegg (USD) — rating + review_count

Newegg shows star ratings and review counts. Both fields are available and meaningful.

🇯🇵
Kakaku (JPY) — review_count only (no rating)

Kakaku.com shows review counts but not simple star ratings. Review volume is used as the popularity proxy.

🇰🇷
Danawa (KRW) — store_count (no ratings at all)

Danawa is a price comparison site. It shows how many stores carry a product — more stores = more popular/established product.

🧠
Why different metrics matter for your AI instructions

When you ask an AI to "add a bestsellers chart to the Korea dashboard," you now know to say: "use store_count as the ranking metric, since Danawa doesn't have review ratings." Being precise about the data schema means the AI makes the right architectural choice the first time.

The deduplification trick

When you scrape multiple pages for the same brand, the same product can appear on both page 1 and page 2. The scraper prevents duplicates using a set — a special data structure that refuses duplicate entries, like a guest list that bounces people who are already inside.

CODE 
seen_names: set[str] = set()

# ... inside the product loop:
key = model.lower()
if key in seen_names:
    continue
seen_names.add(key)
PLAIN ENGLISH

Create an empty set called seen_names. It will track every product name we have already saved.

(Inside the loop, for each product we find:)

Convert the model name to lowercase — so "X870E NOVA WIFI" and "x870e nova wifi" count as the same product.

If this lowercase name is already in our seen_names set, it is a duplicate...

...skip it and move to the next product (the "continue" command jumps to the next loop iteration).

Otherwise, add this name to the set — it's now "registered" and won't be added again.

04

The Dashboard Factory

How Python bakes 750 products into a single self-contained HTML file that works in any browser.

A file that carries its own furniture

Most websites require a web server — a computer that stays running and serves files on demand. But dashboard.html is different: it works when you double-click it in Finder, even with no internet connection. How?

The generator bakes all the data directly into the HTML file as a JavaScript variable. The browser loads the file, reads the embedded data, and renders the entire interactive dashboard — charts, filters, sorts — using only what's already in the file.

📦
Self-contained vs. server-dependent

A typical web app loads data by calling an API. Dashboard.html skips the API entirely — the data is already inside it. The tradeoff: the file is larger (~1MB), and to refresh the data you must regenerate the whole file. But for a daily email attachment, this is the perfect tradeoff.

Python writes JavaScript

The most elegant part of generate_dashboard.py is a single trick: it reads the JSON, converts it to a JavaScript-compatible format, and embeds it inside a <script> tag in the HTML file. Python generates JavaScript.

CODE 
def js_literal(obj) -> str:
    return json.dumps(obj, ensure_ascii=False)

# Inside the HTML template:
return f"""
<script>
const RAW = {js_literal(products)};
</script>
"""
PLAIN ENGLISH

Define a helper function that converts a Python object (list or dictionary) into its JSON text form — which is also valid JavaScript syntax.

ensure_ascii=False means Japanese or Korean characters are kept as-is instead of being escaped.

Inside the big HTML template string we're building...

Write an opening script tag — this tells the browser "JavaScript code follows."

Write "const RAW = " followed by all 750+ products as a JavaScript array literal. When the browser loads this file, RAW becomes available instantly — no network request needed.

Close the script tag.

The browser as a rendering engine

Once the HTML file loads, the JavaScript inside it takes over. It reads the RAW array and dynamically builds every table row, every chart bar, and every KPI card. None of this HTML existed when the file was generated — it's created live by the browser.

1
Page loads, RAW variable is set

The browser parses the script tag and stores all 750 products as a JavaScript array in memory. This takes milliseconds.

2
render() is called

The render() function runs immediately. It passes all products through the active filter settings (brand, chipset, price range...).

3
DOM is populated

renderTable(), renderKPIs(), renderReviewChart() each build their HTML strings and inject them into the page using innerHTML.

4
Filter change → re-render

Every time you change a filter dropdown, render() runs again with the new settings — the whole table rebuilds in under 10ms.

Turning two numbers into one insight

The "Value Score" column in the dashboard is a calculated metric — not scraped from Newegg, but computed fresh each time. It answers the question: "Which board gives the best rating per dollar spent?"

CODE 
function valueScore(p) {
  return p.price > 0
    ? ((p.rating / p.price) * 100).toFixed(2)
    : '0.00';
}
PLAIN ENGLISH

Define a function called valueScore that takes a product (p) as input.

If the price is greater than zero (so we don't divide by zero)...

...calculate: (rating divided by price) multiplied by 100, rounded to 2 decimal places. A 4.6-star board at $259 scores: (4.6/259)*100 = 1.78.

Otherwise (price is zero, no data), return "0.00" to avoid a math error.

End of function.

📐
Derived metrics are a superpower

Raw data shows you what exists. Derived metrics (like value score) reveal relationships the raw data hides. Any time you're combining two columns into an insight — ratio, difference, rank — that's a derived metric. This is one of the most powerful things you can ask an AI to add to a dashboard.

The Mail Room

Environment variables, SMTP, MIME — and how a Python script sends a polished email with a dashboard attached.

The secrets problem

To send an email, the script needs your Gmail address and password. But hardcoding a password directly in a Python file is a serious security risk — anyone who sees the code sees the password. The solution: environment variables.

Think of environment variables as a keychain that lives outside the codebase. The script borrows the key when it needs it, but the keychain itself is never left lying around in the code.

❌

Wrong: hardcoded secret

password = "mypassword123" — anyone who reads or shares the file now has your password.

✅

Right: environment variable

password = os.environ.get("EMAIL_PASSWORD") — the code reads the password from the system at runtime. The password lives only in .env, which is never committed to git.

The .env file: your local secrets locker

The .env file is a plain text file that lives in the project folder. It lists the environment variables you want available when you run the scripts. The python-dotenv library reads this file automatically when the script starts.

.env FILE 
EMAIL_SENDER=you@gmail.com
EMAIL_PASSWORD=abcd efgh ijkl mnop
EMAIL_RECIPIENT=boss@company.com,team@company.com
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
PLAIN ENGLISH

The Gmail address the email is sent FROM. This must be the account whose app password you are using.

A 16-character Gmail App Password — NOT your regular password. You create this in Google Account settings under Security. It looks like 4 groups of 4 letters.

Who receives the email. Multiple addresses are separated by commas — the script splits this string and sends to each one.

Gmail's outgoing mail server address. For Gmail this never changes.

Port 587 is the standard port for SMTP with STARTTLS encryption — secure email submission.

SMTP: the postal protocol

SMTP is the protocol for sending email — the set of rules that governs how email travels from your Python script to Gmail's servers and onward to the recipient.

Building a MIME message: the email sandwich

An email is not just text — it can contain multiple parts: plain text, styled HTML, and file attachments. The MIME standard defines how to package all these parts into one message that email clients can interpret correctly.

CODE 
msg = MIMEMultipart("mixed")
msg["From"]    = SENDER
msg["To"]      = ", ".join(recipients)
msg["Subject"] = subject

alt = MIMEMultipart("alternative")
alt.attach(MIMEText(build_text_body(summary), "plain", "utf-8"))
alt.attach(MIMEText(build_html_body(summary), "html",  "utf-8"))
msg.attach(alt)
PLAIN ENGLISH

Create the outer container for the whole email. "mixed" means it will hold both a body and file attachments.

Set the From header — who the email appears to come from.

Set the To header. If there are multiple recipients, join their addresses with commas.

Set the Subject line — includes the date tag like "[Newegg] Motherboard Dashboard [2026-04-15]".

Create an inner container for the email body. "alternative" means: here are two versions — plain text AND HTML. The email client picks whichever it supports.

Attach the plain-text version — a simple text summary for clients that don't render HTML.

Attach the HTML version — the styled email body with KPI cards, brand table, and picks.

Attach the inner body container to the outer message container.

Attaching the dashboard file

The HTML summary in the email body is designed for mobile — quick scanning on a phone. The full interactive dashboard is attached as a file, meant to be opened on a desktop browser where the filters and charts really shine.

CODE 
html_bytes = DASHBOARD_FILE.read_bytes()
attachment = MIMEApplication(html_bytes, Name="dashboard.html")
attachment["Content-Disposition"] = \
    'attachment; filename="dashboard.html"'
msg.attach(attachment)
PLAIN ENGLISH

Read the entire dashboard.html file as raw bytes (binary data — the computer's native format for files).

Wrap the bytes in a MIME attachment object. Give it the filename "dashboard.html" so email clients know what to call it.

Set the Content-Disposition header — this tells the email client "this is an attachment" (as opposed to inline content that should display in the email body).

The filename appears in the email's attachment tray — what the recipient sees and downloads.

Attach this file to the outer message. The email now has: body text, HTML body, and dashboard.html attached.

🔒
Why App Passwords, not your regular password

Gmail blocks "less secure" direct logins. An App Password is a 16-character code specific to this script. If it ever leaks, you revoke just that code without changing your main password. This is called least privilege — granting only the minimum access needed.
