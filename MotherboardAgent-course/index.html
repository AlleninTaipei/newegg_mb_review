The Report Factory

How one small script turns three websites, in three countries, into three inboxes, every single morning.

Three Countries, One Job

MotherboardAgent watches motherboard listings on three online marketplaces, one based in the United States, one in Japan, one in Korea. Every day, without anyone touching a keyboard, it turns what it finds into a dashboard and emails it out.

🔎
Scrape

A program visits each marketplace and copies down prices, ratings, and listings, the kind of scraping a person would otherwise do by hand.

📊
Build a dashboard

The scraped data gets turned into one clean web page that ranks what's new and what's trending.

📧
Email the report

That dashboard gets emailed to the people who need to see it, with zero manual steps.

Three Foreign Bureaus

Picture a newspaper that runs three foreign bureaus: one in New York, one in Tokyo, one in Seoul. Every bureau follows the same editorial template and the same deadline, but each one reads its local instruments differently, star ratings in one city, review counts in another, store counts in a third.

In the code, that's three regions running the exact same steps on three different marketplaces.

Reading run_all.sh

The whole trick lives in six lines. Each region's function call ends with a trailing &, which turns it into a background process, and $! hands back its PID so the script can check on it later.

CODE 

run_pipeline "Newegg" scraper.py generate_dashboard.py send_email.py &
PID_NEWEGG=$!
run_pipeline "Kakaku" kakaku_scraper.py generate_kakaku_dashboard.py kakaku_send_email.py &
PID_KAKAKU=$!
run_pipeline "Danawa" danawa_scraper.py generate_danawa_dashboard.py danawa_send_email.py &
PID_DANAWA=$!
PLAIN ENGLISH

Kick off the whole Newegg pipeline, scrape then dashboard then email, but the trailing & backgrounds it so the script doesn't wait for it to finish before moving on.

$! is the PID of the job we just backgrounded. Save it as PID_NEWEGG so we can check on it in a moment.

Same idea, for Kakaku: start its pipeline in the background too.

Save Kakaku's PID as well, as PID_KAKAKU.

And again for Danawa: start its pipeline in the background.

Save Danawa's PID as PID_DANAWA.

💡
Key Insight

Starting a task in the background and checking on it later, instead of doing everything one at a time, is called concurrency. It's the entire reason all three regions can finish around the same time instead of one after another.

Why This Matters When You Talk to AI

Once you can see "one pattern, repeated three times," you know exactly what to ask for next. Adding a fourth region means telling an AI assistant to clone the existing pattern, not invent a new one from scratch.

🚩
Red Flag

If you ever see an AI assistant try to make the three regions share state, or block on each other, that's worth questioning. They were designed to be independent, and forcing them to coordinate defeats the entire point of running them at once.

One Motherboard's Journey

Pick one real product and follow it, step by step, from a messy web page all the way into a finished dashboard.

Meet our test subject

Every screen in this module follows the exact same product: an ASRock X870E NOVA WIFI motherboard, as it existed on Newegg back on the day this data was collected.

ASRock X870E NOVA WIFI AM5 socket, X870E chipset, ATX form factor
4.6 stars 282 reviews on Newegg
$259.99 Listed price, in USD

By the end of this module, you will know exactly which file holds this number at every point in the journey, which matters a lot the day one of these numbers looks wrong.

A rigged game of telephone

You know the party game where a whispered sentence gets passed down a line of people, and comes out the other end hilariously wrong. This project plays that same game with data, except it is rigged never to lose fidelity.

Instead of each person whispering whatever they think they heard, every handoff writes the message down in a strict, agreed-upon form, called a schema. That single discipline is what keeps "X870E NOVA WIFI, 4.6 stars, 282 reviews" intact from a raw web page all the way into someone's inbox.

Key insight

Every handoff between files in this project is a structured data handoff, never a fuzzy one, and each step only adds or reshapes fields, it never has to remember the whole page again.

Step 1: reading a star rating out of raw HTML

The Newegg page itself is just HTML, a pile of tags with no concept of "4.6 stars" as a number. The function parse_rating in scraper.py is the first thing that turns that mess into an actual number.

CODE 

def parse_rating(item) -> float | None:
    el = item.select_one(".item-rating i")
    if el:
        m = re.search(r"rated ([\d.]+) out of", el.get("aria-label", ""))
        if m:
            return float(m.group(1))
        # Fallback via CSS class: 'rating-4-5' → 4.5, 'rating-5' → 5.0
        for cls in el.get("class", []):
            m2 = re.match(r"rating-(\d+)-(\d+)$", cls)
            if m2:
                return float(f"{m2.group(1)}.{m2.group(2)}")
            m3 = re.match(r"rating-(\d+)$", cls)
            if m3:
                return float(m3.group(1))
    return None
PLAIN ENGLISH

This is a function that tries to read a star rating from one product listing, and returns a number if it can, or nothing if it can't.

Find the little star icon on the page that displays the rating.

If that icon actually exists on the page.

Use a regex to search the icon's aria-label text for a pattern like "rated 4.6 out of", and pull out just the number.

If that pattern matched, turn the text "4.6" into an actual number and hand it back right away.

If that didn't work, fall back to a second method: read the rating from the icon's CSS class name instead.

Look for a class shaped like "rating-4-5" and convert it to 4.5.

Or a class shaped like "rating-5" and convert it to 5.0.

If nothing at all was found, admit it and return nothing rather than guessing.

Step 4: flattening nested groups into one list

The JSON file organizes products by brand first, which is convenient for saving, but awkward for a dashboard that just wants one big table. So generate_dashboard.py reads the file and flattens it.

PYTHON 

def load_data(path: str) -> tuple[list[dict], dict]:
    with open(path, encoding="utf-8") as fh:
        raw = json.load(fh)

    products = []
    for brand, brand_obj in raw["brands"].items():
        for p in brand_obj["products"]:
            products.append({
                "brand":       brand,
                "name":        p["name"],
                "socket":      p.get("socket", "Unknown"),
                "chipset":     p.get("chipset", "Unknown"),
                "form":        p.get("form_factor", "ATX"),
                "rating":      p.get("rating", 0),
                "reviews":     p.get("review_count", 0),
                "price":       p.get("price_usd", 0),
                "platform":    p.get("category", "Unknown"),
            })
    return products, raw

Our board comes out the other side as one plain entry in a single list, sitting right alongside every other brand's boards, brand label included.

Step 5: Python writes JavaScript, as text

Now comes the strangest handoff in the whole journey. generate_dashboard.py does not send the data anywhere, it writes the data directly into the HTML file it is building, as if it were typing JavaScript source code by hand.

CODE 

<script>
const RAW = {js_literal(products)};
PLAIN ENGLISH

This line is plain HTML, it tells the browser "everything below is a JavaScript program, not text to display."

Wherever {js_literal(products)} appears, Python fills in the real product data before the file is ever saved, so the browser opens the file and finds a fully-formed JavaScript array already sitting there.

js_literal(obj) is simply json.dumps(obj, ensure_ascii=False), a one-line helper that turns a Python list into the equivalent string of JSON text.

Journey's end: a page that needs no server

By the time dashboard.html opens in a browser, the product data is not somewhere else waiting to be fetched, it is already embedded right inside the page.

There is no server to ask, and no waiting, the page can sort, filter, and render its own table the instant it loads.

Why this matters when something looks wrong

Once you can see data flowing through fixed-shape steps, you know exactly where to look first if a number seems off in the final dashboard. You do not have to guess whether the dashboard code is broken.

Ask an AI coding agent to check the middle of the pipeline first, does motherboard_reviews.json already have the right rating, before assuming the last file in line is at fault.

The core debugging skill: bisect the pipeline

To bisect the pipeline means checking a step in the middle of the journey, rather than only the very start or the very end, to cut your search space in half every time.

The same JSON file that feeds the dashboard also feeds send_email.py, which picks the top-rated board straight out of it for the email summary.

PYTHON 

    total_reviews = sum(p.get("review_count", 0) for p in products)

    top_rated = max(
        (p for p in products if p.get("review_count", 0) >= 10),
        key=lambda p: p["rating"],
        default=None,
    )

If our board ever shows up as "top rated" in an email but looks wrong on the dashboard, both features are reading the very same file, so the bug, or the fix, is likely in one shared place.

Four things every crossing needs

Talking to a system you don't own always comes down to the same four concerns.

🛂
The right paperwork

An HTTP header called User-Agent disguises the script as a real browser so the site doesn't reject it.

🗣️
Each country's own dialect

Newegg wants a URL with query parameters attached. Danawa wants a POST payload sent to a specific endpoint.

🔑
A key nobody else holds

Passwords and recipient lists live in environment variables, never hard-coded into a file anyone could read.

🚆
A train that leaves on schedule

A cron schedule kicks the whole pipeline off automatically, with no human required.

Different countries, different customs forms

Newegg only needs a passport at the door. Danawa asks for a filled-out customs form too, a POST payload describing exactly which category, page, and manufacturer to fetch.

Handing over the mail: the SMTP handshake

Sending the finished report isn't one instruction, it's a short conversation with the mail server, step by step.

CODE 
    with smtplib.SMTP(SMTP_HOST, SMTP_PORT) as server:
        server.ehlo()
        server.starttls()
        server.ehlo()
        server.login(SENDER, PASSWORD)
        server.sendmail(SENDER, recipients, msg.as_string())
PLAIN ENGLISH

Connect to Gmail's mail server over SMTP, the standard protocol for handing off email.

Say hello, and introduce yourself in plain, unencrypted text, for now.

Ask to upgrade the connection to an encrypted one before anything sensitive is sent.

Say hello again, this time over the encrypted connection.

Log in with the sender's address and password, now that eavesdroppers can't read them.

Hand over the finished message and the recipient list. The server takes it from here.

Those credentials come from environment variables, never written into the code itself.

CODE 
SENDER     = os.environ.get("EMAIL_SENDER", "")
PASSWORD   = os.environ.get("EMAIL_PASSWORD", "")
RECIPIENT  = os.environ.get("EMAIL_RECIPIENT_NEWEGG", "")
SMTP_HOST  = os.environ.get("SMTP_HOST", "smtp.gmail.com")
SMTP_PORT  = int(os.environ.get("SMTP_PORT", "587"))
PLAIN ENGLISH

Read the sender address, password, and recipient from whatever the running system provides, not from a file in this repository.

If nothing is provided, fall back to Gmail's own standard server address and port.

Variables you can see, secrets you can't

GitHub Actions is the train conductor: it wakes the whole pipeline up on a fixed timetable and hands each job its credentials. It draws a hard line between two kinds of values.

CODE 
on:
  schedule:
    - cron: '0 1 * * 1-5'  # 週一至週五 UTC 01:00（台灣時間早上 9 點）
  workflow_dispatch:       # 允許在 GitHub UI 手動觸發

jobs:
  send-reports:
    steps:
      - name: Run all region pipelines
        run: bash run_all.sh
        env:
          EMAIL_SENDER:           ${{ vars.EMAIL_SENDER }}
          EMAIL_PASSWORD:         ${{ secrets.EMAIL_PASSWORD }}
          EMAIL_RECIPIENT_NEWEGG: ${{ vars.EMAIL_RECIPIENT_NEWEGG }}
          EMAIL_RECIPIENT_KAKAKU: ${{ vars.EMAIL_RECIPIENT_KAKAKU }}
          EMAIL_RECIPIENT_DANAWA: ${{ vars.EMAIL_RECIPIENT_DANAWA }}
PLAIN ENGLISH

Run automatically at 1am UTC (9am Taipei) every Monday through Friday, using cron's five-field schedule syntax. Also allow a human to press a button and trigger it manually via workflow_dispatch.

Run the exact same script the schedule would have run.

The sender address and recipient lists come from vars, plain configuration values anyone with repo access can see in GitHub's UI.

The password comes from secrets, an encrypted value that GitHub shows once when saved and never again, not even to the person who set it.

💡
Variable vs. secret

A Variable is fine to see in plain text, like a recipient's address. A Secret is never fine to see in plain text, like a password. Mixing the two up is one of the most common real-world security mistakes.

Why this matters

Recognizing "this is talking to an external system" tells you where things are fragile and outside this project's control. A site redesign can break scraping overnight, and that's not a bug in this codebase, it's an external dependency risk.

It also hands you the vocabulary, headers, endpoints, payloads, environment variables, secrets, cron, to precisely ask an AI coding agent to "add retry logic around this external call" or "rotate this secret."

The Clever Tricks

A handful of small, reusable ideas do most of the heavy lifting in this codebase, from spotting a chipset buried in messy text to catching a price change overnight.

A product title that hides everything

ASRock X870E Nova WiFi 5G AM5 ATX Motherboard

No box on that listing says "chipset: X870E" in a clean, labeled field. Every time the code sees a title like this, for every brand and every language, it has to figure out the socket, the chipset, and the form factor entirely on its own.

Playing birdwatcher with a blurry photo

A birdwatcher spotting a rare species through the trees doesn't wait for the bird to introduce itself. One distinctive marking, a wing bar, an eye ring, is enough to name the species with confidence.

parse_chipset works the same way: instead of asking the page for a clean field, it scans the messy title for one distinctive marking, an exact chunk of text like "X870E", and the moment it spots one, the identification is done.

CODE 

def parse_chipset(name: str) -> str:

Then walk down a long list of every known chipset code, but in a very deliberate order, most specific first.

Notice there's no regex here, no clever pattern language. Just a plain "is this text inside that text" check, repeated down a carefully ordered list.

Look at that list again: "X870E" sits right before "X870". That's not an accident, it's the whole trick.

💡
Greedy Matching Order

Checking longer, more specific strings before shorter, more general ones is a pattern engineers call greedy matching order. Get the order wrong, put "X870" before "X870E", and every X870E board silently gets misidentified as a plain X870, with no error and no warning, just a quietly wrong answer.

def compute_price_diff() -> list:
    """Return list of (name, old_price, new_price, diff) for changed/new products."""
    if not PRE_FILE.exists() or not DATA_FILE.exists():
        return []
    with open(DATA_FILE, encoding="utf-8") as fh:
        cur = json.load(fh)
    with open(PRE_FILE, encoding="utf-8") as fh:
        pre = json.load(fh)

    def flatten(data):
        result = {}
        for brand_obj in data.get("brands", {}).values():
            for item in brand_obj.get("products", []):
                result[item["name"]] = item
        return result

    cur_map = flatten(cur)
    pre_map = flatten(pre)
    diffs = []
    for name, ni in cur_map.items():
        np = ni.get("price_usd")
        if np is None:
            continue
        oi = pre_map.get(name)
        if oi is None:
            diffs.append((name, None, np, None))
        elif oi.get("price_usd") != np:
            diffs.append((name, oi["price_usd"], np, np - oi["price_usd"]))
    return diffs
PLAIN ENGLISH

First, check both files actually exist. If either the old snapshot or the new one is missing, there's nothing to compare, so give up with an empty list.

Open today's data and yesterday's data, both saved as JSON, a plain-text way of storing structured data.

flatten() digs every product out of its brand grouping and builds one big lookup table, keyed by the product's name, so any product can be found instantly instead of searched for.

Build two of these lookup tables: one from today's data, one from yesterday's.

For every product in today's list, skip anything that doesn't have a listed price.

Look that same product name up in yesterday's table. Never seen before? It's new. Price changed? Record the old price, the new price, and the diff between them.

When Things Break

Every pipeline in this course has worked so far. Real ones don't always. Here's how this codebase tells you what went wrong, and how to read it like a flight recorder.

The black box, not the crash

When a plane has a bad flight, investigators don't rebuild the plane from scratch. They pull the flight recorder and check exactly which system logged an anomaly, and when.

This codebase leaves the same kind of breadcrumbs: print statements, per-region failure messages, and quiet skips instead of guesses. This module teaches you to read them.

Everything worked. Until it doesn't.

Across five modules, every scraper ran, every dashboard built, every email sent. In the real world, websites redesign their pages, network requests time out, and one region's step can fail while the other two succeed fine.

This module is about the signals this codebase already gives you for exactly that moment, so you never have to guess what broke.

Three simple shapes, not one clever framework

This codebase's failure handling is intentionally simple and visible, not clever and hidden. Missing data is silently skipped, one region failing doesn't take down the other two, and a failed step is reported by name.

Recognizing these three shapes helps you tell normal, expected degraded operation apart from an actual bug.

Shape 1: skip, don't guess

When a product's price or rating can't be parsed, the scraper drops that one item rather than saving it with a made-up value like $0.00. It would rather under-report than lie.

CODE

            rating = parse_rating(item)

PLAIN ENGLISH

Try to read this item's price, and try to read its rating.

If either one couldn't be read, meaning it came back empty...

...skip this one item entirely and move to the next. Don't save it with a fake or blank number.

This is a deliberate design choice. A missing motherboard in tomorrow's dashboard is a minor gap; a motherboard listed at a fake $0.00 price is a lie that spreads into every downstream chart and email.

Shape 2: one region's failure stays contained

A network hiccup while scraping one brand is caught as an exception instead of crashing the whole program. It's logged with the brand's name attached, then that one brand's loop stops early.

Print exactly which brand failed and why, then stop just that brand's scrape.

Zoom out one level and the same shape repeats at the shell script level. Each region's chain of scripts reports its own name if it fails, and the final step waits on all three regions individually so one failure never hides the other two's results.

Shape 3: failures are logged by name

run_all.sh never just says "something failed." It says which region and which script, so you know exactly where to look first.

CODE 
run_pipeline() {
    local region=$1; shift
    for script in "$@"; do
        echo "[${region}] ${script} ..."
        if ! python3 "${script}"; then
            echo "[${region}] FAILED at ${script}" >&2
            return 1
        fi
    done
    echo "[${region}] all done"
}
PLAIN ENGLISH

This function runs one region's chain of scripts in order, one at a time.

If any single script in that chain fails, print exactly which region and which script.

Stop that region's chain right there, but don't touch the other regions.

How to debug a failure

When something looks wrong tomorrow morning, work through these four questions in order. Each one points at a specific place to look, not the whole system.

1
Which region failed?

Check run_all.sh's output for a line like [Kakaku] FAILED at generate_kakaku_dashboard.py. That names the exact region and exact script, so you only need AI to look at that one log.

2
Did a product just go missing?

That's usually not a crash. Check whether its price or rating parsed as None and got silently skipped, the same shape you saw above, not a sign the scraper is broken.

3
Did the whole scrape return zero products?

That's a bigger signal. It usually means the website changed its layout, breaking a CSS selector like .item-container or .item-rating i that the scraper depends on to find things on the page.

4
Want to add a 4th region?

Copy the scraper, generator, and sender trio from an existing region, adjust the schema fields for that market's metric (like Danawa's store_count), then add one line to run_all.sh and one recipient variable to the GitHub Actions workflow.

A website redesign is the one failure this codebase can't route around on its own, because it changes the shape of the page the selector was written for. Everything else, missing fields, one bad request, one failed script, is handled by the three shapes above.

💡
Key Insight

This system's resilience doesn't come from one big clever error-handling framework. It comes from small, boring choices made consistently: skip instead of guess, isolate failures per region, and log every failure by name. The simplest failure handling is usually the most debuggable one.
